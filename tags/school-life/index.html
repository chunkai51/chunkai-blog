    一句需求，Codex 干碎了我的开发梦

    因为实在想不到要做什么样的产品，我开始审视自己。作为学生，我们既缺少技术能力，又远离社会生产，甚至人际关系网络也小得可怜，根本就很难发现所谓的痛点嘛，倒是上周骑车把手腕摔伤了挺痛的。 至少就我来说，活这么二十来年，要说对什么领域有“建树”，也就游戏打得比较多。那不如去做点游戏试试，我当然了解玩游戏跟做游戏不是一个概念，但其实也一直都想试试看呢。 我希望学习看起来在越来越主流化的独立游戏开发引擎 Godot 来尝试实现一些想法。跟随官方文档学习了一段时间，我基本了解了 Godot 的界面、项目开发流程、脚本语言，并跟着官方文档的指导做了一个简易但相当完善的躲避飞行物游戏。 我觉得过程中涉及许多与编辑器图形界面交互的操作，想这似乎超出了 Coding agent 的能力范畴，但用 VSCode 一查看，又发现其实这些文件也都是代码，也许是可以力大砖飞的。于是，虽然依然不是正确的使用方式，我还是在一节水课上烦躁地闻着包扎起的手臂散发出的中药味时，抱着电脑放在旁边闲着也是闲着不如玩玩看的态度，想要尝试一句话让 Codex 给我做一个基于 Godot 引擎的游戏出来，看看是否做得到。如果真的有这样的能力，做真正的游戏项目时改 bug 和加拓展也会很有用。 结果它真的做出来了。 而且不是那种“给你糊几段代码，你自己再去编辑器里接半天”的做出来，而是先把一句模糊需求扩成一份相当完整的 plan，再自己往下搭场景、写脚本、修报错、跑验证，最后真把项目跑通了。项目启动起来那一刻我相当惊讶，因为我完全没想到它真的能在这样偏专业的环境里做到这一步，我原本以为至少也要我去配合在编辑器上点击一些操作。 一句话直接被拆成工程 我只说了一句话： 在此godot4项目中开发一个类似vampire survivors的小游戏，按照网上主流的类似练手项目做法，按Godot官方推荐写法 Codex 却把它拆成了一套很像样的工程方案。 它先确认项目几乎是空仓，然后去查 Godot 官方文档和常见练手项目的做法，再把实现方向收敛成几条非常明确的原则： 主体结构以 scene 组合为核心 系统之间优先用 signal 解耦 autoload 只保留最小必要的全局运行态 武器、敌人、升级项这些静态配置放进 Resource 随后，它把目标收得很克制，也很专业：做一个标准练手版的类 Vampire Survivors 小游戏，单地图、单角色、两种武器、2 到 3 种敌人、经验升级、存活计时、暂停和结算，全都围绕“先把玩法闭环搭出来”。 这其实特别像一个靠谱开发者会做的事。不是一上来炫功能，而是先定边界，先确保能跑、能玩、能继续扩展。 不是一坨脚本，而是挺像样的 Godot 项目 后面的实现过程也比我想的更讲究结构。 主场景没有被它写成一个巨大的根节点脚本，而是拆成了 World、Actors、Projectiles、Pickups、UI、Camera2D、Spawner、PauseLayer 这些层次。玩家、敌人、武器、掉落物和 UI 也分别做成了独立场景和脚本。 运行态上，它没有乱堆全局 manager，只保留了一个 RunState autoload，负责本局时间、击杀数、等级和暂停状态这些最小但必要的全局信息。敌人、武器和升级项这些静态配置，则被放进了 EnemyData、WeaponData、UpgradeData 之类的 Resource 里。 哪怕我现在还只是刚学 Godot 没多久，也看得出来这套写法不是随便拼的，而是明显在往“按 Godot 官方推荐习惯来”这件事上靠。 ...

    让 Codex 帮我发公众号，意外地不错？

    因为额度实在不耐用，我也暂时没想到怎么发挥它更大的用处，我便暂停了 Qoder 的订阅，转而奢侈了一把，开通了 OpenAI Plus。这倒是我深思熟虑的选择。网络环境不够健壮，订阅 Claude 被 ban 的风险过大；Claude Code 加国内模型看起来坑还是不少，而且似乎也未必比 Codex 强，来回换 API 渠道、测试 coding plan 的开销也不低；国内工具则大多还在更像 Cursor 的阶段。相比之下，OpenAI Plus 的性价比反而挺高：能高强度用 Codex，能比较放心地用 ChatGPT，还有客户端、多端协同、各种工具，甚至还能接给 OpenClaw 来用。 于是，体验了各种功能，大聊特聊了一些平时因为限额不舍得聊的话题之后，我才想起来我还没怎么认真用过 Codex。做学校课程实验那次不算，我只是把资料丢进工程里，说了一句话，它就连代码带运行结果还有实验报告一起写完了，快得让我根本没形成什么体验。看着剩余的 100% 额度，我甚至有点焦虑。正好那几天刷 Hacker News 又看到有意思的话题，我想，不如试试把之前由 Qoder Work 做的“写公众号”任务迁移给 Codex。它明明是个编程 agent，但也许在 GPT-5.4 的加持下，这件事并不是完全没戏。 真正开始做之后，我发现这件事有意思的地方，不在于“Codex 居然也会写文章”，而在于它把一次写作任务做成了一个很完整的协作过程。我们不只是写了一篇稿子，还顺手补了一套技能、修了一套微信后台注入脚本、重做了一份更适合我自己的写作提示词。最后回头看，这甚至比单独拿到一篇文章更有价值。 第一件事不是写稿，而是先让它理解这个文件夹 我一开始问 Codex 的问题其实很直接：你是个 coding agent，不是写作 agent，那你到底能不能胜任这种任务？如果不能，有没有办法直接调用 ChatGPT 网页版或者客户端来做？ 它没有急着开始输出，而是先看了当前工作区里已经有什么。那一刻我才意识到，这类 agent 做写作和聊天模型最大的区别之一，就是它会先把“环境”也当成任务的一部分。这个文件夹里本来就有我的中文草稿、公众号相关内容、一些风格提示词。Codex 先把这些摸清楚，然后才开始补能力。 后面的动作也很像在配开发环境，只不过对象从代码变成了写作流程。它补了几个本地 skills：一个负责去掉明显的 AI 味，一个负责中文科技长文和公众号改写，一个负责热点文章的联网调研。到这一步为止，Codex 还没有真正起草文章，但它已经不像一个“泛用聊天窗口”，而更像一个正在被调教成写作助手的 agent 了。 这一步其实挺关键。因为我后来越来越觉得，AI 写作里真正麻烦的从来不是“写一段像样的话”，而是让工具先理解你平时写什么、放在哪、怎么改、最后要交付成什么。 真正让我改观的，是它会把写作当成一个项目来做 我给 Codex 的第一次完整任务，是去写 Claude Code 源代码泄漏那篇文章。要求很具体：先从可信英文来源搜集近期信息，再结合社区里比较受欢迎的技术博客去分析，然后把产物放进新文件夹里，不只是要博客草稿，还要公众号排版版本和能直接注入微信公众号后台的脚本。 ...

    究竟该干嘛？

    我有一点沮丧，明明提前了将近一个月接触到 OpenClaw，但由于谨慎或者说是懒，除了写一点垃圾文章以外没有做任何“布局”，以至于没挣着一点儿东西，还不如上闲鱼给人500元包安装包卸载去。 当然老想着搞钱也很无聊，机会很多，能看懂形势找到下一步该怎么做更重要，而我，目前看不出来啥。 听说 Meta 收购了那个 moltbook，这是什么意思，那玩意有什么价值吗，考虑到他们之前还炒元宇宙，我觉得不咋靠谱。但至少 Agent 肯定还是大家都在探索的方向，Meta 作为搞社交平台的，这次收购的目的可能也是要研究 Agent 的交流、协作模式吧。 我呢，目前刚刚勉强搞明白 ReAct、agent、skill、mcp、swe-agent、harness 这些黑话都是什么意思，稍微熟悉了一下 python 语言。学 Agent 最麻烦的是没资源，那些个论文读着似懂非懂，lectures 也听得似懂非懂，问 AI 就让我去做什么 SDK，还要翻 OpenAI、Anthropic的开发者文档……实在不像 Java 那样的成熟体系好学。 至少经过了这两周的东学学西看看，我大概能提炼出接下来的长期安排： 从理论角度学 Agent（听 lectures，学论文，从较高视角理解 Agent） 利用 AI 工具加速学会完整的 Java 后端开发体系（明白后端是在干嘛） 学好数据库和软件工程（明白软件工程师是在干嘛） 复现/开发 Agent 项目（丰富简历） 开始刷题（复习数据结构与算法，避免大脑生锈） 之前的 Agent 学习计划其实可以继续，但基础的软件工程/后端体系一定要学。因为 AI 更新太快，必须要有点根基，才能实现真正的利用 AI 干中学，不然就是被 AI 牵着走，可替代性太高了。可以继续关注技术新闻，写点东西，甚至做点其他产出，找找机会，但不要轻易误了正事。
