    两次烧光 Codex 额度，我意识到做成一个项目没那么简单

    May 6, 2026 · Chunkai

    我依然在改那个扑克筹码工具，本来只是想要让它变得能用，现在尝到了些 AI coding 的正反馈，就不愿停下来，想要一鼓作气把它做成一个真正拿得上台面的“项目”——“无非就是把功能做得更完整，把安全性搞好点，收个口，写些文档而已，应该不会有多麻烦吧！”我天真地认为。毕竟我已经闲到开始做彩蛋了。

    先聊点开心的好了——令我相当满意的“彩蛋”#

    我对筹码的一个小执念，就是要在牌桌上做叠筹码的小动作，感觉很帅很好玩 （其实很吵很傻帽），这也是我喜欢德扑的一点。这个动作叫 Chip riffle，暂且译作“筹码叠洗”。有些线上扑克游戏把这做成了可发送的表情用来交流、搞心态，但我更希望把这个做成有互动性、就好像自己上手去叠一样的小游戏。

    我向 codex 讲清了要做什么，包括一张张穿插叠起的过程，分成两堆又叠回一堆的循环，从下往上堆起，下面的筹码堆叠时上面的会被垫高、倾斜等细节。最后敲定了一套通过点按与滑动触发筹码动画的方案，还加了声效、多种配色，又让筹码能定位而非循环放动画（若用双色筹码可以观察到堆叠时筹码被打乱又逐渐恢复）。

    中间走了些弯路，尤其是音效的问题，我原本使用 web audio 来生成音效，但怎么调都不对味，还始终不能消除掉我的手机上测试时发出的“爆鸣声”。最终选择全部推倒，换成真实音效，没想到开放使用的声音资源还挺多，而且质量非常好。配合上用 web audio 搓音效时形成的逐渐拉高音高来制造“爽感”的经验，最终的效果非常好。

    这个功能与本体没有什么关系，但我觉得这能让这个工具显得更有活力，而且确实挺好玩。

    小改 UI 不如重构逻辑，但麻烦也由此开始#

    在此之前，玩家信息是用卡片状的 box 显示的，在大屏端横向排列，手机端锁定一行一个。我的构想是一个玩家只需要在自己的设备上注意自己的卡片，所以这样处理会很方便、优雅。然而，实际游玩时，我发现玩家会需要连续上下翻找查看轮到谁操作、上个人下了多少等信息的，而手机端巨大的卡片反而成了负担。

    我首先想到的是把卡片缩小、让屏幕里能放下更多，顺便把跟注数额显示出来而不需要去找上个行动的玩家，发现当前未轮到操作的玩家仍然保留不可点按的操作按钮是很占地方的，于是把按钮去掉，把当前操作玩家外的玩家卡片缩成较小的条状卡片，而大屏端保持原本状态。然后……都这样了，不如直接把操作按钮提取到一个固定位置，而玩家卡片部分只显示信息。

    但我发现这样反而不太对劲，因为下面的玩家卡片不再有什么变化，就让网页有了一种不可明状的廉价感。我想要的德州扑克筹码管理工具应该是什么样呢？我头脑中浮现出一个椭圆形的牌桌，玩家围坐在牌桌周围，按顺时针行动——这才像样嘛，当然这也不是我自己想出来的，而是那些线上扑克游戏都长这样，最开始用 copilot 构建的时候实在想不到该怎么实现才没有采用，现在既然已经将操作控制和信息显示分离，玩家卡片可以压缩得更小，采用椭圆形牌桌，大屏端横向排布，手机端纵向排布，效果应当是很好的。

    Codex 对这些有关图形的需求理解也很到位，两次调整就做出了我想要的“较方的椭圆形牌桌”，并且把玩家卡片缩小成了仅包含玩家名、筹码数、下注信息、位置信息的小胶囊，可通过点击来展开浮窗查看详细信息，又把底池、轮次等信息迁移到牌桌中央，计划后面把操作按钮也放在中央……感觉改对了方向，工具的档次将要再提升一截！然而，当我要把玩家卡片放在桌子的合适位置上时，却几乎回到了那个与 copilot 拉扯的燥热夏天。

    玩家排布总是改不合理：不对称、过于拥挤、相互遮挡、挡住中心信息……Codex 开始不总能理解我的要求，我想也许也跟我为了省用量不让用 playwright 自己跑结果有点关系。最后连着改了几组对话，还是不满意，于是我让 codex 直接告诉我在哪改数值，我去手动一个个把排布改到合理的状态，对总共九种（2-10名玩家）排布……

    至少算是搞定了，看到界面如此完善，我决定再改得人性化一些——加入了包括本工具使用说明、德州扑克游戏规则、牌型大小速查表的玩家手册，还有 github 页面、作者信息的页尾标注，然后就兴奋地去找同学、朋友、家人去打牌测试了。

    问题只有真正使用时才能显现出来#

    真正打起牌来，和没有与我一起开发，没有忽略我想当然的事项，甚至不太熟悉扑克规则的“用户”们，暴露出来了许多问题。

    • 圆形排列对于上方的玩家很不友好，因为对他们左右是反的，难与现实牌桌上的人对上；
    • 所有操作都在一个位置，搭配上网络同步有点延迟，很容易想点自己的操作却点了别人的；
    • 我与家人打牌一般打光一个人就停了，但程序不能到这就出错，需要调整位置分配，确保剩下的人还能玩，甚至让打光的人能补码回来；
    • 大家用的乱七八糟浏览器远没有 Chrome 贴心

    还有许多小问题，这次不能再一个个问题去糊，而应该找找问题的共性，得到更有效的解法。

    首先优化 UI，浏览器对弹窗一般都不太友好，会认定为骚扰信息，给出屏蔽选项甚至自动屏蔽，或是吞掉取消键改为直接退出网页 （也搞不懂是什么逻辑），我将所用用到 confirm 和 alert 的弹窗改为了自定义的浮窗，便解决了这个问题，还做了玩家卡片字体调整、中文名词推敲、添加快捷加注窗口不再必须手动输入 *（手机浏览器里调输入键盘又是一个很破坏体验的事情）*等等小修改。

    但真正的问题不在这里，多人游戏中的混乱，不是改点 UI 就能搞定的，我必须要面对一直在逃避的玩家身份系统了。

    玩家身份 + 房间系统#

    误触、视角、筹码数和位置管理、中途离桌、回桌、加减玩家……这些问题当然都可以一个个用小补丁糊好，但每个问题都好像在提醒我应该重新设计一个更合理的房间系统，区分出不同设备所控制的玩家。

    我首先添加了一个牌桌管理界面，让两局游戏中途可以打开它来编辑玩家信息、修改筹码数、添加/删除玩家、调整座次，然后完善了打光离桌、补码回桌的规则。接下来继续利用这个牌桌管理界面，我开始做玩家身份系统——先不用复杂的注册登录，还是以房间为核心，但让创建房间的这一端作为房主，来批准其他加入房间的用户去绑定玩家。玩家绑定完成后再开始游戏，每个设备上对应的玩家就坐在那一端界面的牌桌底。接下来封死权限，让每端只能点击其绑定的玩家的操作，再留出换设备、换浏览器重连后接管玩家的功能。

    再做一些小优化，让正在行动的玩家卡片有明显的动态高光提示，同时正在等待的其他端不再显示点不动的按钮，而是改成动态的“…等待某某行动”状态，再顺便给庄家做每条街发牌的提醒和其他玩家等待的 UI （太有必要了，想不起来发牌的庄家们），最后把确认赢家和开始下一局做成需要房间中所有人确认才生效，尽可能避免出错。

    You look lonely, I can fix that#

    如果真有计划的那么容易就好了，做这些修改时是劳动节假期期间，我还在忙数学建模比赛，再加上之前不加限制用 playwright、不了解对话管理、还去闲的没事写公众号，我彻底用完了这一周的 Codex 额度，需要度过两天没有 Codex 的生活！

    凌晨一点，我同步了最后一次 commit，恍惚地扣上电脑，思考这几天该怎么过，Gmail 忽然响了，是 Open AI 的 Codex 广告——“GPT-5.5实装、更多工作方式……”，真是相当戏剧性。

    当然也就两天而已，看看书、干干别的事情就过去了。我现在在研究怎么利用家里放着的游戏本跑点本地模型来带 Claude Code 或者 Open Code，如果能成功以后再有这种情况也能凑合用一下。

    一个文件塞了五千行代码，真有你的#

    用户数上去之后 Open AI 确实开始想办法挣钱了，但 Codex 绝对不至于这么不耐用。我想最主要的问题，就是工程控制做得太差。我是做好了 README.md 和 PROJECT_NOTES.md，但其实后来一直都在主任务的对话里继续任务；我一开始没意识到随着房间系统的加入和完善，一个文件搞定逻辑是不可能的，上次拆分出 firebase 部分时又草率放过了 main.js 的一千多行代码，现在一看——已经被 Codex 滚雪球成了五千多行。每次检索某个功能的函数都要跨过几千行代码，不费额度才怪。

    于是收假后，处理好课业，我回来改好了 bug，大概做完了房间系统，就开始计划拆分代码——如果要进一步改进项目，比如把这个感觉不是很可靠的 Firebase 改成其他东西来准备推广项目，先把文件拆好一定会更优雅、专业、省额度、方便后续协作。

    Curse you!#

    意想不到的麻烦是真多，接下来几天，我三番五次连不上 Open AI 的后端，Codex 每跑一个任务都要提心吊胆，避免它因为网络问题断掉。实在是烦透了，还好似乎断掉继续不会很费用量，只是总觉得这会对智能水平有影响。

    文件拆分，简直是一个极端向另一个极端#

    我并不知道该怎么拆分，还以为就是把那些函数剪切到其他文件里，原地留个调用就搞定了。开始干才发现这真是个大工程，DOM 元素、全局变量、game、roomId、Firebase、同步函数、其他 UI 函数、事件监听器、音效、弹窗、本地身份……各种可能存在的依赖，简直把这五千多行代码缠在一起了，拆分就是要把原来靠全局变量黏在一起的代码，改成靠明确接口连接，可不是剪切粘贴那么简单。

    Codex 当然也不同意一次到位，而是出了个详细的拆分计划，一步步执行，我需要一步步跟着做测试、提交。

    但做着做着，我感觉不对劲了——main.js 一次减少可怜的几十行，新文件倒是越建越多，都堆在 src/ 里，感觉反而更乱。提交了十多次修改，main.js 还有四千多行，我就忍不住问了一下现在进行到什么程度，接下来打算拆什么。Codex 相当自信地列了一份拆分清单，这下我彻底忍不了了——他接下来打算拆的内容，跟最开始拆的部分相当相似。

    我想到每次拆分 main.js 的一个功能，都留了有原本体量一小半的代码来保持功能正常运行。他不会是打算把这些东西再拆一遍吧！

    我并不理解该怎么把握拆分节奏、进行有效测试，所以对于前面进行的拆分，我觉得有些过于繁琐，因为通常每步都是很小的改动，你也做过了初步的测试，我基本不会测试出问题，你认为是否能更激进一些，步子迈大一些或是一次多进行几步，由你来控制版本确保遇到问题能回溯解决，到真正有质变需要我手动测试时再停下？

    当前的计划与之前进行过的拆分看起来有些熟悉感，我们会不会重复拆分（比如拆了一个功能，又把留在main中的调用拆成另一个文件）或是把某些功能拆得过于细碎（比如按开发习惯应该一个文件搞定的，由于分步过于谨慎拆了很多个文件）？

    实际情况没这么可怕，只是之前在拆纯逻辑、纯 UI ，接下来要拆流程控制，所以文件的命名有点像。但我的直觉也有可取之处——如果下一步再随手加一堆 “controller”，就可能变成：main.js 调 A controller，A controller 又只是转调 B helper，最后文件超级多，理解成本反而上升。要避免 Codex 继续一点一点从 main.js 上“刮代码”，一定得改一改思路。

    我让 Codex 建立好模块结构，而不是把所有东西都堆在 src/里；在 PROJECT_NOTES.md 里强调拆分切块再大一些、拆分出的文件一定是功能完整的，调整了整体的节奏。

    下一步？#

    到目前，我还在按最后一版的计划进行代码拆分，这仍然是个需要分很多步的大工程。

    我希望把这个工具介绍给更多人，当作一个真正的“开源项目”来运营，所以想尽可能让一切显得专业些，比如拆分代码、换一个更安全好用的后端、设计房间的生命周期

    对于工具本身，我已经觉得它没什么问题了，一些很小的优化需要在拆分之后做一下，然后也许就要到下次玩牌才能发现更多问题或想出更多点子了。
