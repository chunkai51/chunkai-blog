    让 Codex 帮我发公众号，意外地不错？

    April 1, 2026 · Chunkai

    因为额度实在不耐用，我也暂时没想到怎么发挥它更大的用处，我便暂停了 Qoder 的订阅，转而奢侈了一把，开通了 OpenAI Plus。这倒是我深思熟虑的选择。网络环境不够健壮，订阅 Claude 被 ban 的风险过大；Claude Code 加国内模型看起来坑还是不少，而且似乎也未必比 Codex 强，来回换 API 渠道、测试 coding plan 的开销也不低；国内工具则大多还在更像 Cursor 的阶段。相比之下，OpenAI Plus 的性价比反而挺高：能高强度用 Codex，能比较放心地用 ChatGPT，还有客户端、多端协同、各种工具，甚至还能接给 OpenClaw 来用。

    于是，体验了各种功能，大聊特聊了一些平时因为限额不舍得聊的话题之后，我才想起来我还没怎么认真用过 Codex。做学校课程实验那次不算，我只是把资料丢进工程里，说了一句话，它就连代码带运行结果还有实验报告一起写完了，快得让我根本没形成什么体验。看着剩余的 100% 额度，我甚至有点焦虑。正好那几天刷 Hacker News 又看到有意思的话题，我想，不如试试把之前由 Qoder Work 做的“写公众号”任务迁移给 Codex。它明明是个编程 agent，但也许在 GPT-5.4 的加持下，这件事并不是完全没戏。

    真正开始做之后，我发现这件事有意思的地方，不在于“Codex 居然也会写文章”，而在于它把一次写作任务做成了一个很完整的协作过程。我们不只是写了一篇稿子，还顺手补了一套技能、修了一套微信后台注入脚本、重做了一份更适合我自己的写作提示词。最后回头看，这甚至比单独拿到一篇文章更有价值。

    第一件事不是写稿，而是先让它理解这个文件夹#

    我一开始问 Codex 的问题其实很直接：你是个 coding agent，不是写作 agent，那你到底能不能胜任这种任务？如果不能，有没有办法直接调用 ChatGPT 网页版或者客户端来做？

    它没有急着开始输出，而是先看了当前工作区里已经有什么。那一刻我才意识到，这类 agent 做写作和聊天模型最大的区别之一，就是它会先把“环境”也当成任务的一部分。这个文件夹里本来就有我的中文草稿、公众号相关内容、一些风格提示词。Codex 先把这些摸清楚，然后才开始补能力。

    后面的动作也很像在配开发环境，只不过对象从代码变成了写作流程。它补了几个本地 skills：一个负责去掉明显的 AI 味，一个负责中文科技长文和公众号改写，一个负责热点文章的联网调研。到这一步为止，Codex 还没有真正起草文章，但它已经不像一个“泛用聊天窗口”，而更像一个正在被调教成写作助手的 agent 了。

    这一步其实挺关键。因为我后来越来越觉得，AI 写作里真正麻烦的从来不是“写一段像样的话”，而是让工具先理解你平时写什么、放在哪、怎么改、最后要交付成什么。

    真正让我改观的，是它会把写作当成一个项目来做#

    我给 Codex 的第一次完整任务，是去写 Claude Code 源代码泄漏那篇文章。要求很具体：先从可信英文来源搜集近期信息，再结合社区里比较受欢迎的技术博客去分析，然后把产物放进新文件夹里，不只是要博客草稿，还要公众号排版版本和能直接注入微信公众号后台的脚本。

    这其实已经不是“写一篇文章”那么简单了，更像是一个小项目。

    而 Codex 在这里表现得比我预期好不少。它会先研究、再落文档、再生成 HTML、再补脚本，中间的文件组织也是完整的。最后我拿到的不是一篇孤零零的 Markdown，而是一整套能接上后续发布流程的东西。

    这件事本身就让我改观了。平时我对很多 AI 写作工具最大的怨念，是它们很会写出一段“像文章的东西”，但很少真的在乎你后面要怎么发、怎么改、怎么复用。而 Codex 在这类任务里反而有优势，因为它天然把“产物”看得很重。

    最大的坑根本不在文章本身，而在微信公众号后台#

    真正让我开始觉得这件事像在“配系统”，而不是“写文章”的，是后面给公众号后台注入排版内容的时候。

    一开始的脚本很正常地打印出一句成功提示，大意是“文章已经注入编辑器”。问题是，界面一点变化都没有。控制台告诉你一切顺利，页面却像什么都没发生。

    这种问题特别像写程序时最烦的那类情况：看起来每一步都对，但系统就是不认。

    后面补了一个诊断脚本去看页面上到底有哪些 contenteditable 节点，结果很快就发现，微信后台那个正文编辑器更像 ProseMirror 一类的内核。也就是说，直接改 innerHTML 只是改了 DOM，并没有真正更新编辑器自己的内部状态。脚本会觉得自己完成了任务，但编辑器根本没把这次变化算成一次“有效输入”。

    找到这件事之后，后面的修法就比较工程化了：先精确找出真正可见的大编辑区，再优先尝试 document.execCommand('insertHTML')，不行才退回到 innerHTML，最后再退回纯文本逐段插入。说起来不复杂，但如果没有前面那个诊断过程，其实很难一下子想到问题出在这里。

    这也是我第一次比较具体地感受到：一个 coding agent 做写作任务的价值，不只是它能写字，而是它碰到这种偏前端、偏自动化的问题时不会直接卡死。

    第二个坑更典型：逻辑没错，字符串坏了#

    第一层问题修完之后，第二层问题马上又来了。

    新的脚本一运行，控制台直接报错：Failed to execute 'atob' on 'Window': The string to be decoded is not correctly encoded.

    这个问题后来证明比前一个更“朴素”，但也很典型。原因并不在微信公众号，而在我和它之间传递脚本的方式。原版本把整篇 HTML 做成了 base64 长字符串，再在浏览器里解码。理论上没问题，实际上长字符串一旦在复制、粘贴、转义过程中稍微损坏一点，atob 就直接报错。

    这次的修法反而更干脆：不再优先走 base64，直接把原始 HTML 字符串内联进脚本里。注入顺序也固定成了 insertHTML -> innerHTML -> insertText。换句话说，不再追求“看起来更优雅”的方案，而是优先追求那个最稳、最不容易在传递过程中坏掉的方案。

    最后这版脚本是成功的。我在控制台里重新执行后，内容终于真正进了微信编辑器。

    这一段对我来说挺有代表性。很多时候 AI 协作的难点不在于宏大能力，而在于这种非常小、非常烦、但又必须解决的细节。能把这类问题陪你修完，和“帮你起个标题”完全不是一回事。

    一个意外收获：我们顺手重做了我的写作提示词#

    写完那篇文章之后，我又发现了另一个问题：文字有点太“会说”了。

    不是说它写得不通顺，而是有些段落明显过热。像“认知”“值钱”“范式”“革命性”“真正的战场”这种词，一旦出现得太频繁，读起来就会有一种作者一直在抢音量的感觉。短视频标题也许需要这种语气，但技术博客和公众号长文一旦这样写，很快就会让人疲劳。

    这一步我本来只想让它帮我压一压措辞，结果后面一路追到了更上游的地方：我原先放在工作区里的提示词，本身就比较偏“爆文导向”，太强调钩子、金句、社交传播性。它们当然不是完全没用，但叠加起来之后，确实会把文章往“很会说”而不是“很可信”的方向推。

    于是后面又做了一轮更彻底的事：结合我自己博客里大部分不是 AI 生成的文章，再广泛看一些成熟技术博客的写法，把原来的两份提示词合并成了一份新的长期版本。新的原则简单很多，也更适合我自己：

    • 可信比炸裂更重要
    • 具体比抽象更重要
    • 先写发生了什么，再写这意味着什么
    • 一篇文章只保留少量真正需要强调的句子

    这一步对我来说反而很有价值。因为它说明，Codex 不是只能在每一篇文章上“局部帮忙”，它还可以顺手把这整条工作流往前推进一点。

    所以，Codex 适不适合拿来做公众号写作？#

    我现在的答案是：适合，但不是那种最直接、最偷懒的“适合”。

    如果你只想打开一个窗口，随口扔个主题，然后等一篇现成的爆款文案掉下来，那 Codex 当然不是最舒服的选择。它毕竟还是一个强烈带着工程气质的 agent。

    但如果你的任务更像下面这些情况，它反而会很好用：

    • 你不只是要一篇稿子，还要研究笔记、排版版、脚本这些后续产物
    • 你要查最新资料，要对来源做区分
    • 你在过程中会遇到技术问题，而且希望工具能接着修
    • 你想让一次任务顺手沉淀成以后还能复用的流程

    在这个意义上，它不是一个“写手型工具”，而更像一个会写作的协作者。

    我现在觉得，前面看着那 100% 的剩余额度发愁，多少有点误会它了。Codex 最值得用的，也许从来就不是“拿来随便写点什么”，而是这种跨了一点写作、又跨了一点研究、还带一点自动化和工程处理的任务。

    把公众号写作迁移给它这件事，至少目前看，并不糟。甚至可以说，意外地不错。
