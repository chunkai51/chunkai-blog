    修复德州扑克筹码计数工具

    April 28, 2026 · Chunkai

    牌瘾依然很大，让我忽然想起十个月前，零前端基础的我用 github copilot 糊出来的那个德州扑克筹码计数器。那玩意的问题依然很大，用起来挺不方便，导致我不好意思让别人用，错过很多玩牌的好机会。

    原来才过去不到一年呐，我和 AI 的进步看来都蛮快的。不如把这玩意改进一下，做到一个真正能用的状态，跟人玩牌就方便多了，还能作为我“作品集”的一员。

    做了这么多测试、牛刀杀鸡、半途而废的小东西之后，也该用 codex 做些至少对我来说意义大一些的工作了。

    Getting on the same page#

    作为早期的ai编程产物，这个项目的代码应当已经在当初改 bug 时堆成了一大坨，我目前也并没有掌握 javascript，自己看不太明白，甚至也记不住有什么 bug 要改了。于是打开 codex 后，先说了：

    请给我讲讲这个项目

    Codex 很机灵地讲了这个玩意的文件结构、工作方式、亮点、缺点，我就告诉它我觉得代码逻辑、安全性、健壮性等有不少问题，请它帮我检查，给出修改建议。

    它一下列出了许多问题，以卡片方式排列，可以看出重要程度、问题简述和详细信息，选择忽略、前往代码。我就开启最高智能等级、高速模式、高权限，直接让它全部解决，又补充让它把之前简陋的手动输入赢家改为按钮选择。

    出乎我的意料，这条命令的用量非常的大。它啃哧吭哧干了十几分钟，修好了全部它检查出的错误和安全隐患，改了上千行代码，又开始调 playwright mcp 去大量测试，直接用掉了 80% 的五小时额度。

    我先赶紧把速度调回标准。去自己再进行测试。

    巧妙或曲折，问题被一个个解决#

    All in 与边池#

    之前一直困扰我的一个问题是 all in 与边池规则，我其实自己都没有想明白要怎么解决——当有玩家筹码不足，进入全下的状态后，若其他玩家继续下注，就形成了边池，若全下的玩家胜利，只能赢走与他对等的筹码，而边池将会留给剩下的玩家争夺。听起来就很绕，我也没跟 LLM 讲明白过，且不知道该怎样高效测试，所以一直做不好。这次我要求把手动输入赢家改为按钮选择倒是歪打正着，codex 随手设计了一个用起来相当直观的底池系统——

    用按钮选择赢家，再按键确定，于是按钮能处于一个待选的状态，避免了误触、允许了多选平分，整体界面也很美观；all in 造成的边池往下排列，排除掉不可选的玩家即可，相当直观。

    在同一个项目上工作，早期的 LLM + IDE 与现在的 coding agent 的对比就相当明显了，Agent 能够不断反问自己，使模糊的想法在思考中扩充成实现，考虑到许多细节，反复验证，确保成功运行

    小修小补，以及每次都要卡我一下的，Git#

    当然也还会有点小问题。可能是记录状态的变量串了，导致弃牌也会被当作开边池的条件。我将这个问题返回给它，顺便让它把牌局记录做成可折叠的盒子，不要把页面越拉越长搞得不美观，另外让它少用用 playwright，太败家了，改完测好就同步到远程仓库去。

    这次偷懒让我有了段奇妙的经历.因为没改到 main branch 上，这次的 commit 需要我再手动融合，然后打开 page 一看，结果竟是修改前和修改后的混合态——有一些明显是刚刚加的功能，但诸如选择赢家等功能却还是旧的方式。

    codex 冷静解答：

    我会先把本地和远端分支状态摸清楚：当前分支、origin/main 最新提交、你现在主分支上到底差了哪些内容。然后我会把已经修好的代码合到 main，再直接推到远端主分支。

    现在看起来远端 origin/main 已经有一个 GitHub 上生成的 merge commit，把我之前的分支合进去了；但本地 main 还停在旧提交。为了排除“页面运行的是主分支但本地/分支不一致”的混乱，我先比较当前分支和远端主分支的实际文件内容。

    文件内容比较结果很关键：当前修好的分支和 origin/main 的树是一样的，说明之前的合并本身没有丢文件内容。你看到 GitHub Pages “有些变有些没变”，更像是 Pages 部署/缓存或主分支构建没有被重新触发。为了按你的要求“直接推主分支”，我会基于最新 origin/main 做一个主分支上的直接提交来触发 Pages 重新部署，而不是再走 PR。

    果然是不学数理化处处是魔法，至少解决了，重新配置 FireBase 之后，也能通过联网同步了。

    真正的核心，联网同步#

    而联网同步扯出来的这些问题，是我去年放弃这个项目的最主要原因。

    网络延迟、操作冲突导致的状态问题和逻辑错误有时会严重影响体验。我还不知道实际的产品要怎么实现这样的功能，我只需要一个简单的按房间号同步状态与操作。codex 简化了 firebase 的配置，通过各种记录状态的变量修改好了这些问题。然而又有点矫枉过正，出现了提交操作的这端反而不能继续操作，需要在其他端才有权限的问题。最终通过增加刷新动作避免卡在中间状态，同步过程中严格禁用玩家操作，以及写入失败或被其他设备抢先更新时，会尝试从远端恢复而不是保留本地脏状态这些逻辑修改，把这些漏洞堵死。

    其实应该更早做的，拆分文件#

    我简单测试，已经发现不了问题了

    翻一翻代码，已经一千多行了，于是我新开一个对话，要求 codex 分析代码是不是应该拆分一下，它说如果以后还会拓展功能就建议现在拆，我说那就拆，它就拆了，拆完我一看，还是一千多行，不过藏到src文件夹里了，行吧，主要是得把 firebase 的配置拆出来我想。

    你就是干这个的👍#

    接下来，看着这个朴素的页面，我觉得应当改一改，虽然这个我自己研究出来的绿色格子还挺可爱，但我想 ai 做这个应当会优秀的多。

    开一个新对话问问界面怎么优化，关键词是“扑克味”、“高级感”，给出的方案不错，就让它执行了。

    结果虽说还是有一些 AI 味，但相当达到我的预期了，尤其是手机端用起来舒服多了，配色颇有些高级德扑桌垫和复古金边筹码的味道。顺手做了个图标，立马就感觉完成度很高了。

    最后，修改 README.md 成一个比较专业的样子之后，这次的重置就可以圆满结束了。

    如果你想看看成果，点这里！

    局限性不是工具的，是我的#

    我用 codex 做过简单的命令行小游戏，又给那个游戏嵌入了 agent，做过课程实验，做过 Godot 游戏，写过文章，做过许多好像很厉害但其实很表层的事情。这次虽然也不能说深到了什么程度，但我姑且可以称之为一个“东西”了——有精美的用户界面，实现了每个功能，支持了联网同步……最重要的是，能真正发挥作用。

    我也一定程度上探到了 codex 的局限性，即便只是一个一千多行代码的小项目，因为开启了高速，配额很快就耗尽，只能等到五小时后继续；上下文窗口也感觉相当有限。我学习了保持主对话专门处理连续开发、架构理解、长期 TODO；定期更新 PROJECT_NOTES.md 等文档来记录项目状态、顶层规则、修改记录；当任务相对独立时开新对话处理。

    把 codex 当成一个无所不能的大活人 （这两个词好像也压根拼不到一起） 的日子该结束了，工程化、专业化才能提高效率，发挥出它的能力。而这些原则和经验，并不是靠遇到问题就问 ChatGPT 能掌握的。
