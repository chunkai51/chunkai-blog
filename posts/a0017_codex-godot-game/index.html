    一句需求，Codex 干碎了我的开发梦

    April 18, 2026 · Chunkai

    因为实在想不到要做什么样的产品，我开始审视自己。作为学生，我们既缺少技术能力，又远离社会生产，甚至人际关系网络也小得可怜，根本就很难发现所谓的痛点嘛，倒是上周骑车把手腕摔伤了挺痛的。

    至少就我来说，活这么二十来年，要说对什么领域有“建树”，也就游戏打得比较多。那不如去做点游戏试试，我当然了解玩游戏跟做游戏不是一个概念，但其实也一直都想试试看呢。

    我希望学习看起来在越来越主流化的独立游戏开发引擎 Godot 来尝试实现一些想法。跟随官方文档学习了一段时间，我基本了解了 Godot 的界面、项目开发流程、脚本语言，并跟着官方文档的指导做了一个简易但相当完善的躲避飞行物游戏。

    我觉得过程中涉及许多与编辑器图形界面交互的操作，想这似乎超出了 Coding agent 的能力范畴，但用 VSCode 一查看，又发现其实这些文件也都是代码，也许是可以力大砖飞的。于是，虽然依然不是正确的使用方式，我还是在一节水课上烦躁地闻着包扎起的手臂散发出的中药味时，抱着电脑放在旁边闲着也是闲着不如玩玩看的态度，想要尝试一句话让 Codex 给我做一个基于 Godot 引擎的游戏出来，看看是否做得到。如果真的有这样的能力，做真正的游戏项目时改 bug 和加拓展也会很有用。

    结果它真的做出来了。

    而且不是那种“给你糊几段代码，你自己再去编辑器里接半天”的做出来，而是先把一句模糊需求扩成一份相当完整的 plan，再自己往下搭场景、写脚本、修报错、跑验证，最后真把项目跑通了。项目启动起来那一刻我相当惊讶，因为我完全没想到它真的能在这样偏专业的环境里做到这一步，我原本以为至少也要我去配合在编辑器上点击一些操作。

    一句话直接被拆成工程#

    我只说了一句话：

    在此godot4项目中开发一个类似vampire survivors的小游戏，按照网上主流的类似练手项目做法，按Godot官方推荐写法

    Codex 却把它拆成了一套很像样的工程方案。

    它先确认项目几乎是空仓，然后去查 Godot 官方文档和常见练手项目的做法，再把实现方向收敛成几条非常明确的原则：

    • 主体结构以 scene 组合为核心
    • 系统之间优先用 signal 解耦
    • autoload 只保留最小必要的全局运行态
    • 武器、敌人、升级项这些静态配置放进 Resource

    随后，它把目标收得很克制，也很专业：做一个标准练手版的类 Vampire Survivors 小游戏，单地图、单角色、两种武器、2 到 3 种敌人、经验升级、存活计时、暂停和结算，全都围绕“先把玩法闭环搭出来”。

    这其实特别像一个靠谱开发者会做的事。不是一上来炫功能，而是先定边界，先确保能跑、能玩、能继续扩展。

    不是一坨脚本，而是挺像样的 Godot 项目#

    后面的实现过程也比我想的更讲究结构。

    主场景没有被它写成一个巨大的根节点脚本，而是拆成了 World、Actors、Projectiles、Pickups、UI、Camera2D、Spawner、PauseLayer 这些层次。玩家、敌人、武器、掉落物和 UI 也分别做成了独立场景和脚本。

    运行态上，它没有乱堆全局 manager，只保留了一个 RunState autoload，负责本局时间、击杀数、等级和暂停状态这些最小但必要的全局信息。敌人、武器和升级项这些静态配置，则被放进了 EnemyData、WeaponData、UpgradeData 之类的 Resource 里。

    哪怕我现在还只是刚学 Godot 没多久，也看得出来这套写法不是随便拼的，而是明显在往“按 Godot 官方推荐习惯来”这件事上靠。

    玩法闭环也接得很完整：

    • 玩家用 CharacterBody2D 处理移动、受伤和无敌帧
    • 敌人统一基类处理追击、受伤、死亡掉经验
    • 武器系统拆成控制器、配置和实体表现
    • 首发就做了两把武器，一把是自动锁定最近敌人的远程投射物，一把是绕身旋转的近战伤害体
    • 升级系统做成 3 选 1，升级时暂停主循环
    • 刷怪按时间分段加权，控制场上数量，避免后期直接炸掉

    这已经不是“生成一个 demo”那么简单了，至少从练手项目的角度看，它搭的是一套可以继续往上加内容的原型。

    还是那些烦人的小问题，但它真的能修好#

    如果它只是一次性生成了四十多个文件，我可能会觉得“好厉害”，但还不至于被震到。真正让我改观的，是它没有在“差不多写完了”那里停下，而是一直顺着问题往下修。

    这里面最有代表性的，不是什么宏大能力，而恰恰是一些很琐碎、但做 Godot 时很真实的坑。

    比如它很快就发现，PackedScene.instantiate() 出来的对象如果被推断成 Node 或 Area2D，后面直接调自定义方法，在 Godot 4 的静态检查里很可能过不去。还有一些跨脚本自定义类型、@export 变量标注、数组构造和循环写法的问题，在编辑器里也许看着还好，到了 headless 解析时就会变得更挑剔。

    这类问题一点也不酷，但特别说明问题。因为真正开发的时候，最耗人的往往不是“把功能写出来”，而是把这些不会出现在宣传视频里的小错一个个磨平。

    它甚至还顺手处理了一个我很在意的细节：升级项如果耗尽，不能把游戏卡死在暂停态，要有兜底逻辑。这种地方特别能看出，人不是完全可以被拿掉的。正是因为我自己有一点点 Godot 学习经验，知道什么地方容易出体验问题，才有可能提出这种要求；而 Codex 也确实能把这种要求接进去，继续改。

    不只写完了，还想办法确保“这玩意真能跑”#

    后面的动作让我觉得最专业。

    它在做完静态清理之后，没有只说一句“理论上应该没问题”，而是去找本机有没有 Godot 可执行文件。确认有 Godot.app 之后，它直接跑了 headless 检查，还跑了一个带自动退出的短时启动验证。

    大致就是这样两步：

    godot --headless --quit
godot --headless --quit-after 180

    前者解决的是“项目能不能被 Godot 正常解析”，后者更接近“主场景真正启动之后，会不会立刻在初始化阶段报错”。

    这一步非常关键。因为很多问题不是写代码时暴露的，而是场景真正载入、节点真正连接、信号真正发射以后才会冒出来。它能想到继续往这一步做，说明它不是把“输出文件”当交付，而是把“可运行”当交付。

    我原来最不看好的，恰恰就是这一点。我以为这种涉及 Godot 编辑器工作流的事情，再怎么说也得我手动参与一些节点连接、资源检查、场景点击。结果它居然真靠代码和命令行把大部分事情都推过去了。

    我的信心如何被干碎，又重建起来#

    兴奋之余，我不禁又陷入悲观。我究竟要学到什么程度，才不能被指挥 AI 一句话得到的产出秒杀呢？就连我自己写的那个 2D 游戏项目，也是靠问 AI 才分析出我找了一小时的 bug。

    但仔细想想其实也没有那么可怕。

    这个游戏本来就是很常见的练手项目，大家在学游戏开发时可能都会做，有丰富的案例、明确的内容。Codex 也确实不是凭空变魔术，而是从一开始就先把我的一句话命令扩大成了一个完善的 plan，锚定类似项目、Godot 官方文档这些参考资料，才能一口气写出一个能跑的项目。

    也正是因为我已经有了几天学习 Godot、完成练习项目的经验，才能提出“按 Godot 官方推荐写法”、补充升级选项耗尽兜底逻辑这类正确的需求。换句话说，这个强大到让我恐惧的产物，其实不是 AI 自己很强的证明，而是开发者与 coding agent 精明协作所涌现出的巨大开发效率提升的小小预演。

    在如今，Coding Agents 既能简单处理上层设计任务，又保持优秀的命令行工作能力，还拓展了把泛泛指令拆成可执行工程步骤的计划模式。模糊想法借助 coding agents 工程化落地，会越来越有法可依。而人如果是那种把一切都全然不管地丢给 AI 来做的人，是不可能发挥出这些价值的。熟悉技术，有自发思考，能持续进行接管、修正、选择，而不是被“AI 式谄媚”哄到失去判断的人，才能够驾驭这样的工具。

    所以我还是想继续学，也想慢一点#

    我将会继续学习 Godot，同时构思我想做的游戏，也会继续尝试在生活中发现需要被解决的问题。

    与技术重回蜜月期，又与强大的 Codex 几次共事，我不再像一个月前那样焦虑，急切地想要做出些什么唬人的东西了。毕竟手现在打字都得一个个往出蹦，才没什么斗志。比起急着让 AI 从各种地方洗稿、赶紧给我变出一个漂亮成果，我现在反而更愿意慢下来。

    AI 能“秒杀”的，也许就只是学校里那些无聊的作业任务而已。至于真正想做的东西，真正想学会的东西，真正会让我在意很久的东西，还是得自己慢慢来。

    正如现在在周末的空教室嘬着咖啡，听着 Apple Music 首页随手点的 “Jazz Chill” 歌单，敲着这篇文章。窗外偶尔有高铁驶过，看着挺有意思，好像还带起了点舒服的微风。这就足够了，没必要非得坐上那高铁借着那速度去哪里嘛，我一会儿还要去治手呢。
